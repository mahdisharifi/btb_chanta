# پایداری پایگاه داده، صف قیمت ارزی و بازیابی شعبه‌ها

تاریخ بررسی و اجرای اصلاح: ۲۰۲۶/۱۱/۱۲، به وقت تهران. محیط تأییدشده: Windows، XAMPP و `MariaDB 10.4.32`؛ اتصال Laravel از نوع `mysql` است. این گزارش نسخهٔ سرور Production را تعیین نمی‌کند.

## ماهیت و ارتباط اجزا

`ApplySupplierCurrencyPriceChunk` یک کار صف برای اعمال نرخ ارز تأمین‌کننده بر گروهی از پیشنهادهای فروش اوست. شناسه‌های ورودی، شناسهٔ `product_supplier` هستند؛ این کار محصول مرجع جدید ایجاد نمی‌کند. تنظیم نرخ ارز، ارز انتخابی تأمین‌کننده، نسخهٔ تنظیم نرخ و نسخهٔ قیمت‌گذاری تعیین می‌کنند کار هنوز معتبر است یا باید نسل جدید صف شود.

پس از پردازش، کار صف، قیمت‌های ذخیره‌شدهٔ همان گروه را برای هماهنگ‌سازی شعبه‌های وابسته می‌خواند و به‌روزرسانی نمایش قیمت‌ها را صف می‌کند. حتی نسل منقضی‌شده نیز ممکن است برای تازه‌سازی قیمت‌هایی که قبلاً ذخیره شده‌اند، وارد همین مسیر هماهنگ‌سازی شود. بنابراین خطا در خواندن شعبه‌ها می‌تواند پیش از اعمال نرخ جدید هم ظاهر شود.

زنجیرهٔ مرتبط:

`ApplySupplierCurrencyPriceChunk → dispatchChunkBroadcast → SupplierBranchPriceSyncService::syncBranchesForPrimaryPrices → activeBranches → suppliers`.

خواندن شعبه‌ها با `FOR UPDATE` داخل تراکنش است تا تغییر قیمت شعبه با تغییر قیمت مبنا تداخل نکند. حذف تراکنش یا قفل، راه‌حل این اشکال نیست. شعبهٔ مستقل از مسیر دریافت خودکار قیمت مبنا کنار گذاشته می‌شود؛ پیشنهاد فروش و قیمت هر شعبه همچنان به شناسهٔ تأمین‌کنندهٔ خودش تعلق دارند.

`active_branch_name` ستونی محاسباتی برای قید یکتایی است:

```sql
CASE WHEN is_active = 1 AND deleted_at IS NULL
     THEN branch_name ELSE NULL END
```

قید یکتای `(parent_supplier_id, active_branch_name)` فقط نام شعبه‌های فعال و حذف‌نشدهٔ یک فروشگاه را رزرو می‌کند. نام شعبهٔ غیرفعال یا حذف‌شده قابل استفادهٔ مجدد است. نام یکسان در فروشگاه دیگر نیز مجاز است. هنگام فعال‌سازی یا بازیابی شعبه، برخورد با نام فعال موجود باید رد شود.

## علائم، شواهد و علت تأییدشده

- کار صف با `MySQL server has gone away` متوقف می‌شد. ثبت خطا در `failed_jobs` نیز گاهی به علت قطع کامل اتصال ممکن نبود.
- در ۱۲:۳۳:۳۶، Windows Application Event Log از منبع `MariaDB` خطای زیر را برای جدول `suppliers` ثبت کرد. خطا با استثنای `0x80000003` به توقف فرایند `mysqld.exe` منجر می‌شد:

```text
InnoDB: Clustered record field for column 44 not found
MySQL table suppliers field name DB_ROW_ID
```

- پرس‌وجوی ثبت‌شده، انتخاب تمام ستون‌های شعبه با شرط والد، مالک، فعال بودن و حذف‌نشدن، همراه با `ORDER BY id ASC FOR UPDATE` بود.
- خاموش کردن سایت و صف، اجرای بدون خطای MySQL را ممکن می‌کرد؛ اجرای دوبارهٔ کار صف همان مسیر خطا را فعال می‌کرد.
- خطا روی کپی کامل فایل‌های دیتابیس، با همان نسخهٔ MariaDB و روی پورت جداگانهٔ `13307` بازتولید شد.
- بازسازی ساده با `ALTER TABLE suppliers FORCE, ALGORITHM=COPY` کافی نبود: پرس‌وجوی مستقل عبور کرد اما اجرای کامل Job دوباره باعث توقف نسخهٔ آزمایشی شد.
- تبدیل ستون محاسباتی دارای ایندکس از `VIRTUAL` به `STORED` با حفظ عبارت و قید یکتایی، اجرای کامل Job را پایدار کرد.

نتیجهٔ قابل اتکا، ناسازگاری مسیر خواندن قفل‌شده با ساختار دارای ستون `VIRTUAL` در محیط آزمایش‌شده است. Job محرک خطای موتور بود. شمارهٔ یک باگ مشخص در MariaDB یا اینکه تنها علت، الگوریتم `INSTANT` بوده، با این آزمایش تعیین نشده است؛ نباید آن را به‌عنوان واقعیت قطعی گزارش کرد.

## اصلاح و اثر آن بر داده‌ها

۱. migration ایجاد قید نام فعال برای MySQL/MariaDB از `storedAs` استفاده می‌کند. مسیر SQLite همچنان ستون `VIRTUAL` دارد، چون افزودن ستون ذخیره‌شده با `ALTER TABLE` در SQLite مسیر قابل اتکای این پروژه نیست.

۲. migration افزودن حالت قیمت‌گذاری شعبه در MySQL/MariaDB الگوریتم `COPY` را صریح انتخاب می‌کند؛ مسیرهای دیگر همچنان از Schema Builder استفاده می‌کنند. مسیر برگشت همین migration نیز از بازسازی صریح استفاده می‌کند.

۳. migration جدید `2026_11_12_130000_store_active_branch_name_on_mariadb` محیط‌های قبلاً نصب‌شدهٔ MariaDB سری `10.4` را اصلاح می‌کند. در نسخه‌های دیگر و SQLite عملی انجام نمی‌دهد. اگر ستون از قبل ذخیره‌شده باشد، تغییر دوباره‌ای اعمال نمی‌کند. اگر ستون لازم وجود نداشته باشد، با خطای واضح متوقف می‌شود.

این migration در یک دستور `ALTER ... ALGORITHM=COPY` ایندکس و ستون محاسباتی را با همان نام، نوع، عبارت و قید یکتایی بازایجاد می‌کند. شناسهٔ شعبه، مالک، والد، نام، وضعیت، آدرس و سایر داده‌های تأمین‌کننده حفظ می‌شوند. محتوای `products`، ارتباط‌های فروش `product_supplier` و مبلغ‌های `product_prices` در این migration موضوع ویرایش نیستند. اجرای عادی Job پس از اصلاح، همچنان می‌تواند قیمت‌ها را طبق تنظیمات مجاز کاربر به‌روز کند.

برگشت migration بازیابی، ستون را دوباره `VIRTUAL` نمی‌کند؛ قاعدهٔ کسب‌وکار ثابت می‌ماند و بازگرداندن ساختار مشکل‌دار، هدف rollback نیست. برای بازگردانی کامل محیط، بازیابی پشتیبان مستقل لازم است.

## پشتیبان و روش اجرای همین محیط

پیش از تغییر دیتابیس اصلی:

- در حالت خاموش MySQL، از کل پوشهٔ داده و تنظیم اولیه نسخه پشتیبان گرفته شد: ۱۶۳۰ فایل، مجموع ۴۲۶٬۳۷۳٬۵۰۹ بایت. مسیر و اندازه و SHA-256 تک‌تک فایل‌ها با منبع تطبیق داده شد.
- یک کپی دوم برای آزمون جدا شد؛ هیچ آزمایش بازتولید خطا روی تنها نسخهٔ پشتیبان انجام نشد.
- پس از اجرای MySQL اصلی، خروجی کامل SQL پایگاه پروژه، شامل ساختار، داده، trigger، routine و event تهیه شد: ۲۵٬۹۵۰٬۶۵۵ بایت. فایل خصوصی است و نباید وارد Git یا فضای عمومی وب شود.
- تمام ۳۲ رکورد تأمین‌کننده و تعریف جدول، پیش از اصلاح جداگانه ثبت شد.

مسیر محلی مدارک و پشتیبان این رخداد:

```text
storage/app/private/mysql-recovery-20261112/
  cold-backup/
  cold-backup-sha256.json
  my-original.ini
  before-repair.sql
  metadata-3306.json
  suppliers-3306-before.json
```

سرور آزمایشی از کپی `sandbox-data` روی `127.0.0.1:13307` استفاده کرد. اتصال اصلی روی `3306` ماند؛ تنظیم `.env` پروژه برای استفاده از کپی تغییر نکرد. در بازپخش آزمایشی، صف و رخدادها fake شدند و کش آرایه‌ای بود تا پیام بیرونی یا تغییر کش اصلی رخ ندهد. این آزمایش، تحویل واقعی پیام‌ها یا WebSocket را تأیید نمی‌کند.

پس از عبور آزمون‌ها و با خاموش بودن پردازش‌های سایت، فقط migration اصلاحی روی دیتابیس اصلی اجرا شد:

```powershell
php artisan migrate --path=database/migrations/2026_11_12_130000_store_active_branch_name_on_mariadb.php --force --no-interaction
```

اجرای `migrate:rollback` کلی، حذف فایل‌های InnoDB، جایگزینی پوشهٔ داده با backup پیش‌فرض XAMPP و استفاده از `innodb_force_recovery` در این بازیابی انجام نشد. نیازی به حذف محصول، حذف شعبه یا حذف تمام صف نبود.

## نتیجهٔ کنترل‌ها

| کنترل | نتیجهٔ ثبت‌شده |
|---|---|
| تطابق پشتیبان سرد با فایل‌های منبع | ۱۶۳۰ فایل برابر با SHA-256 |
| بازتولید خطای موتور | روی کپی مستقل؛ موفق |
| بازسازی سادهٔ جدول | برای اجرای کامل Job ناکافی |
| سه Job موجود در نسخهٔ آزمایشی | هر سه موفق؛ شامل ۲۵، ۲۵ و ۱۵ پیشنهاد فروش؛ بازپخش دوباره نیز موفق |
| رگرسیون migration روی MariaDB واقعی | نصب تازه، ارتقای VIRTUAL، اجرای تکراری، rollback و ۴۰ خواندن قفل‌شده موفق |
| قواعد نام فعال | تکرار فعال رد شد؛ غیرفعال/حذف‌شده و فروشگاه دیگر مجاز؛ غیرفعال‌سازی نام را آزاد کرد |
| دادهٔ تأمین‌کنندهٔ اصلی پس از migration | هر ۳۲ رکورد با تمام مقادیر قبلی برابر؛ SHA-256 برابر |
| تعریف اصلی جدول | فقط `VIRTUAL → STORED`؛ نام ایندکس‌ها، کلیدها، ستون‌ها و سایر تعریف‌ها حفظ شد |
| `CHECK TABLE suppliers` روی دیتابیس اصلی | `OK` |
| Jobهای اصلی باقی‌مانده | دو اجرای واقعی worker، هر دو `DONE` در ۱۲:۵۷:۴۷ و ۱۲:۵۷:۴۸ |
| تعداد `failed_jobs` قبل و بعد از worker | ۱۵ → ۱۵؛ خطای جدیدی اضافه نشد |
| سلامت اتصال اصلی پس از worker | پورت ۳۳۰۶ پاسخ داد؛ MySQL متوقف نشد |

دو worker اصلی با `--once` اجرا شدند و فقط دو کار اول صف که از همین نوع بودند پردازش شدند. کارهای نامرتبط صف تخلیه نشدند. `queue:retry all` اجرا نشد و ۱۵ خطای تاریخی موجود، موضوع پاک‌سازی این اصلاح نبودند.

رگرسیون خودکار مخصوص ذخیره‌سازی، یک دیتابیس با نام تصادفی روی **سرور دورریختنی** می‌سازد و در پایان فقط همان دیتابیس را حذف می‌کند. پورت `3306` را نمی‌پذیرد:

```powershell
php tests/Smoke/BranchPricingStorageCheck.php --port=13307
```

تست را به دیتابیس اصلی یا Production متصل نکنید. آزمون Jobهای معتبر/منقضی، نمایش نهایی قیمت در فروشگاه، PDF، جستجو و تحویل پیام‌ها، افزون بر کنترل ساختار لازم است؛ قواعد نمایش را مطابق [نمایش و مصرف‌کنندگان](09-visibility.md) و [قیمت‌گذاری و هماهنگ‌سازی](08-pricing-sync.md) بررسی کنید. ستون نام فعال خودش در فهرست محصول یا قیمت به کاربر نمایش داده نمی‌شود؛ اثرش بر ساخت، نام‌گذاری، فعال‌سازی و بازیابی شعبه است. قیمت حاصل از Job، در همان مسیرهای مصرف قیمت پیشنهاد فروش هر شعبه استفاده می‌شود.

## حدود و منابع فنی

SQLite خطای داخلی InnoDB را بازتولید نمی‌کند؛ موفقیت Smokeهای حافظه‌ای جای تست MariaDB واقعی را نمی‌گیرد. تست ارتقای ستون مشکل‌دار روی `10.4.32` اجرا شده؛ سایر نسخه‌های موتور و محیط Production مستقلاً باید تأیید شوند. ارتقای خود MariaDB یا XAMPP در این تغییر انجام نشده است.

مستندات رسمی مورد رجوع: MariaDB، «Generated Columns» برای تفاوت VIRTUAL و STORED و ایندکس‌های آن‌ها؛ «InnoDB Online DDL Operations with the INSTANT Alter Algorithm» برای بازسازی ذخیره‌سازی؛ و «InnoDB Recovery Modes» برای محدودیت‌های recovery. این منابع، باگ مشخصی را برای رخداد حاضر اثبات نمی‌کنند؛ نتیجهٔ عملی فوق از لاگ محلی و آزمایش قبل/بعد به دست آمده است.
