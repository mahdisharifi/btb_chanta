# بازبینی مستقل API و یکپارچه‌سازی دسته‌بندی

تاریخ: ۲۰۲۶-۱۰-۲۵. محدوده: API دسته‌بندی v1 به‌عنوان مصرف‌کنندهٔ همان مدل و مقایسه با کاتالوگ وب. صفحهٔ `/categories` با Blade رندر می‌شود و جست‌وجوی آن Alpine محلی است (`resources/views/pages/categories/index.blade.php:36` به بعد)؛ مصرف مستقیم `/api/v1/categories` در resources/app/tests پیدا نشد. بنابراین اختلاف‌های زیر **خرابی مستقیم اتصال این صفحه به API نیستند**؛ مصرف‌کنندهٔ خارجی API بررسی نشده است.

## A1 — P2 / متوسط در صورت انتظار هم‌ارزی کاتالوگ وب و API: دستهٔ مادر در API خالی و در وب دارای کالا است

- محل: `app/Http/Controllers/Api/V1/CategoryApiController.php:36` از `$category->products()` فقط کالاهای مستقیم را می‌خواند؛ در مقابل `app/Http/Controllers/Web/CategoryController.php:82` و `:87` شناسهٔ تمام descendants و خود دسته را وارد query می‌کنند.
- شاهد اجرایی فقط‌خواندنی روی دادهٔ فعلی: برای root با id=1، تعداد کالاهای فعال مستقیم **۰** و تعداد کالاهای فعال خود دسته و descendants **۱۱۹۱** است. اجرای مستقیم `CategoryApiController::show` برای همان مدل، `data.products.total=0` برگرداند. API index نیز برای root اول `products_count=0` داشت.
- بازتولید: slug root دارای کالای صرفاً زیرشاخه را از `/api/v1/categories` انتخاب کنید و GET `/api/v1/categories/{slug}` را با صفحهٔ `/categories/{slug}` مقایسه کنید؛ API به همان دسته از منظر کالاهای مستقیم نگاه می‌کند و وب به زیر‌درخت.
- اثر: کلاینتی که می‌خواهد همان پیمایش کاتالوگ وب را بازسازی کند، در سطح مادر نتیجهٔ خالی دریافت می‌کند، در حالی که وب کالا نشان می‌دهد. وجود اختلاف قطعی است؛ اینکه direct-only یک قرارداد عمدی API است یا نقص محصول، بدون مستندات/کلاینت خارجی قطعی نیست. این مورد باید با مالک دامنه بسته شود و نباید بدون این تصمیم، باگ قطعی صفحهٔ وب معرفی شود.
- پیشنهاد: قرارداد direct در برابر subtree صریح شود؛ اگر هدف نمایش همان کاتالوگ است، منطق scope مشترک برای شناسه‌های دسته و فیلترهای محصول استفاده شود. برای حفظ مصرف‌کنندهٔ موجود، تغییر scope با پارامتر/نسخهٔ سازگار و آزمون دستهٔ مادر و برگ انجام شود. اگر API عمداً direct است، تفاوت مستند و در صورت نیاز مسیر/فیلد subtree جدا افزوده شود. در این بازبینی هیچ قرارداد یا پاسخ تغییر نکرد.

## رفتار خطا: تست واقعی در HTTP kernel برنامه

برای slug ساختگی و ناموجود `__review_missing_category__`، GET روی `/api/v1/categories/...` از HTTP kernel خود برنامه اجرا شد؛ اتصال شبکه/Chrome دخیل نبود:

- با `Accept: application/json`: وضعیت **۴۰۴** و Content-Type **application/json**؛ فیلد message حاضر بود. در محیط debug محلی، فیلدهای exception/file/line/trace هم وجود داشتند؛ این شاهد افشای production نیست و متن آن‌ها در گزارش منتشر نشده است.
- با `Accept: */*`: وضعیت **۴۰۴** و Content-Type **text/html; charset=utf-8**؛ کلاینتی که بدون بررسی status/content-type مستقیماً JSON parse کند، خطای parse می‌گیرد.

این تفاوت در کد پشتیبانی می‌شود: `bootstrap/app.php:50` و `:51` مسیر API را از بازنویسی صفحهٔ خطای برند خارج می‌کنند ولی JSON را اجباری نمی‌کنند. چون در مخزن قرارداد اجباری JSON بدون Accept یا کلاینتی با این فرض پیدا نشد، این را باگ قطعی مستقل حساب نکردیم. کلاینت باید Accept مناسب بفرستد و پیش از parse، HTTP status را بررسی کند؛ اگر محصول JSON را برای همهٔ خطاهای API تضمین می‌کند، shouldRenderJsonWhen بر اساس api/* و تست خطا باید به قرارداد اضافه شود.

## بررسی واقعاً اجراشده و محدودیت‌ها

اجرا شد: خواندن CategoryApiController، routes/api و مسیر وب و relationهای Category؛ جست‌وجوی مصرف‌کننده و تست API دسته‌ها در app/resources/tests؛ queryهای شمارش مستقیم و subtree و اجرای index/show کنترلر روی دادهٔ واقعی؛ دو درخواست GET ناموجود از HTTP kernel با Accept متفاوت.

اجرا نشد: نوشتن API یا داده، درخواست احراز هویت، تغییر status/active، تست کلاینت خارجی/موبایل، audit تمام APIهای پروژه، تست compatibility نسخهٔ آینده، آزمایش رقابت تغییر داده و pagination. هیچ تست خودکار موجود برای CategoryApi در جست‌وجوی محدود پیدا نشد؛ ادعای پوشش کل suite نمی‌شود. این گزارش به‌تنهایی تأیید کارکرد مصرف‌کنندهٔ خارجی نیست.
