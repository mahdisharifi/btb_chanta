# سیاست Barge-in و بی‌اعتبارسازی

## ترتیب اولویت

با تشخیص گفتار تازه، مرورگر ابتدا sourceهای Web Audio و پخش‌های HTML audio را متوقف می‌کند و دادهٔ بافرشده را پاک می‌کند. سپس `cancel_tts_generation` را با `session_id` نشست WebSocket، `turn_id` پاسخ و `generation_id` همان صوت می‌فرستد و HTTP stream و درخواست LLM قبلی را جداگانه abort می‌کند. میکروفون در تمام مدت capture فعال می‌ماند.

## نسل قدیمی

سرور فقط cancellationای را می‌پذیرد که هر سه شناسه با job فعال مطابقت داشته باشد. در Piper:

- کار صف‌شده فوراً از صف برداشته می‌شود.
- صدای buffered بلافاصله purge می‌شود.
- فراخوانی ONNX درحال اجرا قابل‌لغو امن نیست؛ خروجی دیررس دور ریخته می‌شود و slot تا پایان فراخوانی آزاد نمی‌شود.
- یک generation قدیمی نمی‌تواند پس از قطع به همان نشست صوت تازه تحویل دهد.

مرورگر نیز هنگام خواندن هر chunk، `isCurrent` را بررسی می‌کند؛ turn نامعتبر شده یا پاسخ با شناسهٔ مورد انتظار منطبق نباشد، پخش نمی‌شود.

## LLM و ابزار

TTS و LLM دو `AbortController` مستقل دارند. سیاست فعلی هنگام barge-in هر دو را لغو می‌کند تا پاسخ منسوخ هزینه‌زا نباشد؛ لغو صدا به‌تنهایی الزاماً مستلزم لغو reasoning مدل نیست، اما continuation سروری با `task_id` در این نسخه پیاده‌سازی نشده است. ابزار محصولی هم ثبت نشده است.

`ToolExecutionRegistry` فقط interface آزمایشی دارد: read-only/idempotent قابل لغو‌اند؛ side-effecting/irreversible لغو یا تکرار خودکار نمی‌شوند و از idempotency key استفاده می‌شود. برای افزودن ابزار واقعی باید نتیجه و وضعیت اجرای آن مستقل از WebSocket حفظ شود.

## معیار آزمایش مرورگر

برای سنجش «زمان تا قطع شنیداری»، timestampها باید از یک clock مرورگر گرفته شوند: زمان تشخیص barge-in و زمان توقف `AudioBufferSourceNode`. timestamp مرورگر را مستقیماً از monotonic timestamp سرور کم نکن؛ آن‌ها clockهای مجزا هستند.
